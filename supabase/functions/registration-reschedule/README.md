# Registration rescheduling

`POST /context` reads the registration identified by the `x-reschedule-token` capability. `POST /confirm` rechecks the current published course calendar and atomically moves that registration. Tokens are random 256-bit capabilities, stored only as SHA-256 hashes; the student page keeps them in the URL fragment and memory. Tokens expire, can be revoked, and become idempotent receipts after confirmation.

Owner-authenticated endpoints: `lookup`, `issue`, `block`, `revoke`, `health`, `retry-confirmations`. The owner page is `/admin/reschedule.html`. Issuing a link does not send mail or move a student. Before issuing links for multiple disrupted sessions, block all those session IDs so one affected cohort is not offered another unavailable class. `deadlineAt` optionally limits the selected class start; `expiresAt` controls link validity, independently.

Same-course transfers preserve the canonical supersession history, requirements, payment order, material choice, and public-order student references. Exact duplicate imports for the same customer, course, and original start are retired in the transaction; conflicting duplicate financial/completion records require review. No new checkout is created.

The server uses the current published family calendar, then checks canonical session state, date closures, blocked sessions, capacity and active checkout holds. It matches both external session identity and Eastern start time. Published dynamic appointments for BLS Initial, BLS Renewal, and Heartsaver First Aid CPR AED are offered without creating sessions. Confirmation re-fetches the selector and passes only its exact server-validated offer to the service-only dynamic RPC. The browser supplies a selection ID, never booking facts. An empty calendar has a private help-request path.

The dynamic RPC revalidates course, active canonical instructor/location, the exact instruction/consumption interval, publication lease, deadline, closures, blocks, seat inventory, and active checkout holds. The existing selector remains authoritative for instructor qualifications, Google availability, travel and room eligibility; an explicit canonical qualification revocation overrides it. The current canonical resource registry is empty, so new reservations conservatively block the whole Shipyard venue and the instructor at every venue. No room relocation is inferred. Explicit selector cooldown edges may share only the named source's completed instruction boundary.

Confirmation takes the public-checkout offer lock, serializes canonical schedule writes, rechecks availability after waiting, and reuses or materializes the canonical target before calling `confirm_registration_reschedule` in the same database transaction. A new target follows the existing native public-offer materialization pattern and is unlisted. BLS Initial retains its established six-seat booking cap; Renewal and Heartsaver use their own canonical course capacities. No public order or payment is created. Any transfer error rolls back the new target. Stable selection receipts permit replay without requiring a still-current selector publication.

The database change is `20261019225039_registration_reschedule_dynamic_offers.sql`, generated with Supabase CLI `migration new`. Apply the reviewed database change before deploying the updated Edge Function.

Confirmation messages are inserted in the transfer transaction and delivered through the existing `RESEND_API_KEY`. Optional `RESEND_FROM_EMAIL` overrides the established notification sender. Provider idempotency uses the durable message ID. Failed sends never roll back a successful seat move. The page accurately distinguishes saved changes from sent confirmation email. Delivery leases prevent parallel sends; ambiguous attempts beyond the provider deduplication window require review.

The confirmation workflow retries every ten minutes using the existing owner automation credential. Its HTTP failure is a failed Actions run. Health levels must be reported separately: database tests and deployment do not prove recipient delivery or an observed scheduled recovery. Verify the workflow runs, its notification/observer path, and a real recipient confirmation before calling the process monitored or healthy.

Validation: `node --test tests/reschedule.test.mjs`; `tests/reschedule-transaction.sql` inside `BEGIN`/`ROLLBACK` as `service_role`; `node tests/reschedule-browser.mjs` requires Playwright and Chromium. Never run the SQL fixture outside a rollback transaction. Rollback: revoke issued links, remove the public page, disable the confirmation workflow; retain all supersession/audit/financial history.

Dynamic validation: on an empty disposable local PostgreSQL 16 database, load `tests/helpers/reschedule-production-schema.sql`, both original rescheduling migrations, then the dynamic-offer migration and `tests/reschedule-dynamic-transaction.sql`. For two-client checks use a second empty localhost database named `reschedule_concurrency_test`, load the same definitions, set `RESCHEDULE_TEST_DATABASE`, and run `node tests/reschedule-dynamic-concurrency.mjs`. These tests use production-derived columns/defaults/PK/unique/check constraints and exact transfer functions; they omit foreign keys and triggers and do not substitute for a full-schema staging check. CI runs the synthetic checks in an isolated PostgreSQL service. No test sends mail or changes production registrations.
